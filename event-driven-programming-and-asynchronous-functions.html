    11. Event-driven programming and asynchronous functions

    An asynchronous function is a function whose execution is initiated but whose result is not awaited. When execution is complete, the asynchronous function emits an event and transmits its result via that event.

    This mode of operation is well-suited for execution within a web browser. Indeed, an application running within a browser is an event-driven application: the application reacts to events, primarily triggered by the user (clicks, mouse movements, text input, etc.). Javascript applications running within a browser are designed to communicate with external services via the HTTP protocol. The native HTTP functions of Javascript are asynchronous: they are launched, and the receipt of a response from the requested external service is signaled by an event that is added to the set of events managed by the application.

    The following scripts will be executed by [node.js], not by a browser. [node.js] also has an event-driven execution mode:

    • [node.js], like a browser, uses an event loop to execute a script;
    • execution of the script’s main code is the first event executed;
    • if this main code has launched asynchronous tasks, execution continues until these asynchronous tasks are completed. These tasks emit an event when they are completed. These events are queued in the event loop;
    • the main script must subscribe to these events if it wants to retrieve the results of the asynchronous actions;
    • the script is not finished until all events it has emitted have been processed;

    11.1. script [async-01]

    The following script demonstrates the behavior of a script containing an asynchronous action.

    
'use strict';
 
// imports
import moment from 'moment';
import { sprintf } from 'sprintf-js';
 
// start
const débutScript = moment(Date.now());
console.log("[début du script],", heure());
 
// setTimeout sets a 1000 ms timer (2nd parameter) and immediately returns the timer number
// when the timer has run out of 1000 ms, it emits an event which is queued by the runtime
// when the event is processed by the runtime, the function (1st parameter) is executed
setTimeout(function () {
  // this code will be executed when the timer reaches value 0
  console.log("[fin de l'action asynchrone setTimeout],", heure(débutScript));
}, 1000)
 
// will be displayed before the internal timer function msg
console.log("[fin du code principal du script],", heure(débutScript));
 
// time and duration display utility
function heure(début) {
  // current time
  const now = moment(Date.now());
  // time formatting
  let result = "heure=" + now.format("HH:mm:ss:SSS");
  // is it necessary to calculate a duration?
  if (début) {
    const durée = now - début;
    const milliseconds = durée % 1000;
    const seconds = Math.floor(durée / 1000);
    // format time + duration
    result = result + sprintf(", durée= %s seconde(s) et %s millisecondes", seconds, milliseconds);
  }
  // result
  return result;
}

    • line 14: when the script runs, the function [setTimeout] is executed:
      • line 17: a 1000 ms timer is started and the countdown begins until it eventually reaches 0. The [setTimeout] function terminates as soon as the timer is initialized and the countdown begins. It does not wait for the countdown to end. It returns a number identifying the timer used, and execution proceeds to the next instruction, line 20. Here, the result of [setTimeout] is not used;
    • line 16: this message will be displayed at the end of the 1000 ms delay of the [setTimeout] function;
    • lines 15–16: the function f, the first parameter of the [setTimeout] function, will be executed at the end of the 1000 ms delay. The message on line 16 will then be displayed;
    • line 20: this message will be displayed before the one on line 16;

    • line 23: the function accepts an optional parameter [heure], which is the start time of an operation whose duration it must display;
    • lines 25–27: the current time is calculated and formatted;
    • line 29: if the parameter [début] is present, then a duration must be calculated;
    • line 30: the duration of the operation. This yields a number of milliseconds;
    • lines 31–32: this number of milliseconds is broken down into seconds and milliseconds;
    • line 34: the duration is added to the time;

    The [setTimeout] function will allow us to simulate asynchronous tasks in a [node.js] environment. In fact, the [setTimeout] function behaves like an asynchronous task:

    • it returns a result immediately—in this case, a timer number—using the standard function mechanism (return);
    • it may later (which is not yet the case above) return other results via events that are then processed by the event loop of [node.js];
    • in most of the cases that follow, there will be two such events:
      • an event that could be called [success], which will be emitted by the asynchronous task that successfully completed its task. A piece of data—the result of the task—is associated with the emitted event;
      • an event that could be called [failure], which will be emitted by the asynchronous task that failed to complete its task. A piece of data—typically an object describing the error—is associated with the emitted event. Possible errors with an asynchronous internet task, for example, would be “network unavailable,” “server not found,” “timeout exceeded,” etc.
    • The main code that launched an asynchronous task can subscribe to the events that this task is likely to emit. When one of these is emitted, the main code is notified and can trigger the execution of a specific function designed to handle the event. This function receives as a parameter the data that the asynchronous task associated with the emitted event;

    11.2. script [async-02]

    In this script, the asynchronous function [setTimeout] will emit events to communicate data to the code that has subscribed to them.

    Accessing the events of [node.js] requires additional libraries. We choose the [events] library, which we install along with [npm]:

    The [async-02] script is as follows:

    
'use strict';
 
// asynchronous functions can return a result by emitting an event
// the main code can retrieve these results by subscribing to the events issued
 
// imports
import moment from 'moment';
import { sprintf } from 'sprintf-js';
import EventEmitter from 'events';
 
// start
const débutScript = moment(Date.now());
console.log("[début du script],", heure());
// an event transmitter
const eventEmitter = new EventEmitter();
 
// setTimeout sets a 1000 ms timer (2nd parameter) and immediately returns the timer number
// when the timer has run out of 1000 ms, it emits an event which is queued by the runtime
// when the event is processed by the runtime, the function (1st parameter) is executed
setTimeout(function () {
  // this code will be executed when the timer reaches value 0
  console.log("[setTimeout, fin du timer d'1 s],", heure(débutScript));
  // an event is issued to indicate that a result is available
  eventEmitter.emit("timer1Success", { success: 4 });
  // another event is issued to indicate that another result is available
  eventEmitter.emit("timer1Failure", { failure: 6 });
}, 1000)
 
// subscribe to evt [timer1Success]
eventEmitter.on('timer1Success', (result) => {
  console.log(sprintf("la fonction asynchrone du timer a rendu le résultat [%j], %s, via l'événement [timer1Success]", result, heure(débutScript)));
});
 
// subscribe to evt [timer1Failure]
eventEmitter.on('timer1Failure', (result) => {
  console.log(sprintf("la fonction asynchrone du timer a rendu le résultat [%j], %s, via l'événement [timer1Failure]", result, heure(débutScript)));
});
 
// will be displayed before the msg of evts issued by the function associated with [timer1]
console.log("[fin du code principal du script],", heure(débutScript));
 
// time and duration display utility
function heure(début) {
  // current time
  const now = moment(Date.now());
  // time formatting
  let result = "heure=" + now.format("HH:mm:ss:SSS");
  // is it necessary to calculate a duration?
  if (début) {
    const durée = now - début;
    const milliseconds = durée % 1000;
    const seconds = Math.floor(durée / 1000);
    // format time + duration
    result = result + sprintf(", durée= %s seconde(s) et %s millisecondes", seconds, milliseconds);
  }
  // result
  return result;
}

    • line 9: we import the [EventEmitter] class from the [events] library. This is a new feature: until now, we had only imported literal objects and functions;
    • line 15: we create an event emitter [node.js] by instantiating the class [EventEmitter] with the keyword [new];
    • lines 20–27: the asynchronous function [setTimeout]. It will emit two events during execution:
      • line 24, the event [timer1Success] with the associated value {success : 4};
      • line 26, the event [timer1Failure] with the associated value {failure: 6};
      • an asynchronous function can emit as many events as it wants. We mentioned earlier that most often it emits one of the two events [success, failure], not both as we are doing here;
    • line 20: the execution of [setTimeout] is instantaneous: a timer is set and its ID returned to the calling code. The events will be emitted later, in this case 1 second later;
    • Sending events is pointless if there is no code to handle them when they occur. This is why the main code must subscribe to both [timer1Success, timer1Failure] events if it wants to manage them, specifically to retrieve the data associated with these events;
    • lines 30–32: the main code subscribes to the [timer1Success] event. When the [node.js] event listener processes this event, it will call the function that is the second parameter of the [eventEmitter.on] method, passing it the data (here called [result]) associated with the [timer1Success] event;
    • line 31: the event handler function will display the jSON of the data associated with the event as well as the current time;
    • lines 35–37: using similar code, the main code subscribes to the event [timer1Failure];
    • Subscribing to an event (1st parameter) does not immediately execute the code of the [callback] function (2nd parameter). This function will only be executed after the event has occurred;
    • Line 40: The main script code has finished, but the script itself has not, since the main code launched an asynchronous task. The overall script will not finish until this asynchronous task has completed;

    11.3. script [async-03]

    The following script shows another aspect of the [node.js] event loop:

    • the loop executes events one after another, generally in the order they arrive. Some OS scripts assign priorities to events, which are then processed in order of priority rather than order of arrival;
    • the loop executes only one event at a time. The next event is processed only after the previous one has finished. In an event-driven system, you should therefore avoid writing code that monopolizes the processor for long periods, as events will not be processed when they occur but later when the event loop reaches them. This results in an application that is not very “responsive”;

    The script [async-03] demonstrates an example of this phenomenon:

// the main code can retrieve these results by subscribing to the events issued

// when the timer has run out of 1000 ms, it emits an event which is queued by the runtime
// when the event is processed by the runtime, the function (1st parameter) is executed
setTimeout(function () {
  // this code will be executed when the timer reaches value 0
  console.log("[setTimeout, fin du timer d'1 s],", heure(débutScript));
  // an event is issued to indicate that a result is available
  eventEmitter.emit("timer1Success", { success: 4 });
  // another event is issued to indicate that another result is available

  console.log(sprintf("la fonction asynchrone du timer a rendu le résultat [%j], %s, via l'événement [timer1Failure]", result, heure(débutScript)));

    • This code is from the previous example [async-02], to which lines 39–44 have been added;
    • Lines 20–27: The function [setTimeout] has been programmed to execute an internal asynchronous function after a delay of one second. After this second has elapsed, the execution of the timer’s asynchronous function does not occur immediately: an event is placed in the execution loop to request it.     11.4. script [async-04]

    The script [async-04] demonstrates another mechanism, called [Promise], a result promise. This mechanism avoids the need to explicitly handle [node.js] events. It is handled implicitly, and the developer can therefore ignore the existence of these events. However, understanding them will help the developer better grasp the functioning of [Promise], which is complex at first glance.

    The [Promise] type is a Javascript class. Its constructor accepts as a parameter an asynchronous function to which it passes two parameters traditionally called [resolve] and [reject]. They could have different names;

    • The constructor of [Promise] does two things:
      • it creates an event to trigger the execution of the [function(resolve, reject)] function passed to it as a parameter but does not wait for its result and immediately returns a [Promise] object to the calling code. This object can have four states:
        • [pending]: the asynchronous action that returned [Promise] is not yet complete;
        • [fulfilled]: the asynchronous action that returned [Promise] has completed successfully;
        • [rejected]: The asynchronous action that returned [Promise] failed;
        • [settled]: The asynchronous action that returned [Promise] has completed;

    When the constructor returns its result, the created [Promise] object is in the [pending] state, awaiting the results of the asynchronous function;

    • (continued)
      • The asynchronous task in lines 2–5 is launched immediately. Asynchronous tasks are most often input/output tasks that break down as follows:
        1. execution of synchronous code to initiate the I/O operation with another component, such as a remote server;
        2. waiting for a response from that component;
        3. processing this response;

    It is phase 2—waiting for the external component—that is the most resource-intensive. Rather than waiting:

    • the receipt of the data requested from the external component will be signaled by an event;
    • in the synchronous code following phase 1 (line 7 of the example code), we will subscribe to this event and then, at some point, return to the event loop of [node.js]. The next event in the list of pending events will then be processed;
    • During phase 2, there is parallel execution, but on different devices:
      • the processor for the event loop;
      • an external device (disk, database, remote server) for retrieving the requested data;
    • At the end of phase 2, once the I/O operation has obtained the requested data, an event is triggered to indicate that the I/O result is available. This event then joins the others in the event queue;
    • when its turn comes, it will be processed. The function associated with this event (line 7 of the example code) will then be executed;

    This mode of operation helps avoid downtime: the situation where the processor waits for a response from a device that is slower than itself;

    • (continued)
      • once the asynchronous task in lines 2 and 5 has been launched and has completed its work, it can return a result to the calling code using the two functions [resolve, reject] that the constructor [Promise] passed to it as parameters. The convention is as follows:
        • the asynchronous task signals success via [resolve(result)]. This amounts to placing an event—which we could call [resolved]—in the event loop of [node.js], with [result] as the associated data;
        • the asynchronous task signals a failure via [reject(error)]. This amounts to placing an event—which we could call [rejected]—into the event loop of [node.js], with [error] as the associated data, typically an object detailing the error that occurred;
        • the calling code must therefore subscribe to both of these events to be notified when the result of the asynchronous function is available;

    After the asynchronous task encapsulated in [Promise] has finished executing, the state of the [promise] object returned by the [Promise(…)] constructor changes:

    • the [resolved] event changes it from the [pending] state to [resolved];
    • the event [rejected] changes its state from [pending] to [rejected];

    Subscription to the [resolved] and [rejected] events of the asynchronous task is performed using methods of the [Promise] class with the following syntax:

    promise.then(f1).catch(f2).finally(f3);

    where:

    • f1 is a function executed when the state of [promise] changes from [pending] to [resolved], i.e., when the asynchronous task has successfully completed its work. It receives the value [result] as a parameter, passed by the [resolve(result)] instruction of the asynchronous task;
    • f2 is a function executed when the state of [promise] changes from [pending] to [rejected], i.e., when the asynchronous task has failed to complete its work. It receives the value [error] as a parameter, passed by the [reject(errror)] instruction of the asynchronous task;
    • f3 is a function executed after the methods [then] or [catch] have been executed, so it is always executed. It receives no parameters;

    This syntax completely hides the events to which we subscribe. However, it is a subscription, and like the one in the previous example, it does not immediately execute the [f1, f2, f3] functions. These will be executed—or not—when one of the [resolved, rejected] events to which we subscribe occurs.

    The [async-04] script demonstrates this mechanism:

    11.6. script [async-06]

    This new script demonstrates how using the [async / await] keywords together allows for asynchronous code that resembles synchronous code. Event handling is completely hidden, making the code easier to understand.

    We’ll revisit the previous example with the following modifications:

    • we add a third asynchronous function [async03], which returns its result using the [Promise.reject] method, thereby signaling to the event loop that it has “failed” to complete its task;
    • we execute the three asynchronous functions [async01, async02, async03] sequentially. In the previous example, we had executed the asynchronous functions [async01, async02] in parallel;
    • Before the appearance of the keywords [async/await], the sequential execution of asynchronous actions was performed using nested [Promise] functions. As soon as there were several asynchronous actions to execute in this way, the number of promises increased accordingly and the code became less readable;
    • with the keywords [async/await], the sequential execution of asynchronous tasks uses a syntax similar to that of synchronous task execution: 
    
// asynchronous function - using async / await
async function main() {
  // sequential execution of asynchronous tasks
  try {
    // execution while waiting for [async01]
    const result1 = await async01(...);
    console.log("[async01 result]=", result1);
    // execution while waiting for [async02]
    const result2 = await async02(...);
    console.log("[async02 result]=", result2);
    // execution while waiting for [async03]
    const result3 = await async03(...);
    console.log("[async03 result]=", result3);
  } catch (error) {
    // one of the asynchronous actions has failed
    console.log(sprintf("[sequential error]= %j, %s", error));
  } finally {
    // completed
    console.log("[fin exécution séquentielle des tâches asynchrones],");
  }
    • line 6: the asynchronous function [async01] is launched (using the await keyword) and we wait for it to publish its result via one of the [Promise.resolve, Promise.reject] methods. This is therefore a blocking operation;
    • line 6: the keyword [await] transforms the asynchronous operation [async01] into a blocking operation. We know that the operation [async01] returns a result in two ways:
      • It returns a [Promise] object to the calling code almost immediately;
      • it subsequently publishes a result to the event loop via the [Promise.resolve, Promise.reject] methods. It is this latter result that [result1] retrieves, line 6. The event handling for the [async01] action has become invisible;
      • if the result [result] of [async01] is published by [Promise.resolve(result)], it is assigned to [result1] on line 6 and execution continues on line 7;
      • if the result of [async01] is published by [Promise.reject], this causes an exception and code execution jumps to line 14, the catch block. The parameter of the [catch] clause is the error object (error) published by [async01] with an expression [Promise.reject(error)]. The asynchronous task can also publish the error via a [throw(error)]. The [error] object is the one retrieved in [catch(error)];
      • the keyword [await] must be within a function preceded by the keyword [async], line 2. This keyword indicates that the function [main] is an asynchronous function;
      • in the expression [await f(…)], [f] must be an asynchronous function that returns an object [Promise] to the calling code;
    • We do the same for the asynchronous action [async02] on line 9 and [async03] on line 12;

    Still using the keywords [async / await], it is possible to execute asynchronous tasks in parallel using the following syntax:

    
try {
    // parallel execution of asynchronous tasks
    const result = await Promise.all([async01(...), async02(...), async03(...)]);
    console.log(sprintf("[parallel success], %s, result=%j", heure(débutParallel), result));
  } catch (error) {
    // one of the asynchronous actions has failed
    console.log(sprintf("[parallel error], %s, erreur=%j", heure(débutParallel), error));
  } finally {
    // completed
    console.log(sprintf("[fin exécution parallèle des tâches asynchrones],%s", heure(débutParallel)));
}
    • line 3: there is a blocking operation: we wait for the three asynchronous tasks in the [async01(..), async02(..), async03(..)] array to publish their results to the event loop using one of the [Promise.resolve, Promise.reject] methods;
    • if the three asynchronous tasks publish their results using [Promise.resolve], then the constant [result] is the array [result1, result2, result3] where:
      • [result1] is the result published by [async01] using the expression [Promise.resolve(result1)];
      • [result2] is the result published by [async02] using the expression [Promise.resolve(result2)];
      • [result3] is the result published by [async03] with the expression [Promise.resolve(result3)];
    • if any of the three tasks publishes its result with the expression [Promise.reject(error)], then an exception occurs;
      • the constant [result] on line 3 does not receive a value;
      • execution proceeds directly to [catch] on line 5;
      • the parameter (error) of the catch block is the object (error) published by the expression [Promise.reject(error)];

    By combining these two syntaxes, you can execute asynchronous tasks either sequentially or in parallel, all using syntax similar to that of synchronous code. This syntax is therefore much more readable than the previous ones and should be preferred. This [async / await] syntax has only been available since version 6 of ECMAScript. There is still a lot of Javascript code that uses [Promise] promises. That is why it is also important to understand how they work.
